Getting Market Partner live

The site is six static HTML pages — no server, no database, nothing to run. This guide takes it from where it sits today (hosted as private preview pages) to a real, fast, HTTPS site at marketpartner.com, via GitHub for version control and AWS for hosting.

01–02

Source control

Get the code into a GitHub repo, so every change is tracked and nothing lives only on one machine.

03–06

Hosting

S3 stores the files, CloudFront serves them fast over HTTPS worldwide, and DNS points your domain at it.

07–08

Keep it current

A GitHub Actions workflow pushes every future change live automatically — no manual re-upload.

00

What's ready already

Attached to this conversation is marketpartner-static-site.zip — download and unzip it before starting. It contains:

  • index.html plus the five service pages, with every internal link already rewritten to plain relative filenames (no more claude.ai URLs) — this was the one code change needed before the site can live anywhere else.
  • .github/workflows/deploy.yml — a ready-made GitHub Actions workflow that syncs the site to S3 on every push. It's inert until you add the AWS secrets described in phase 07.
  • README.md — a short recap of this same structure, for future reference inside the repo itself.
Nothing else needs to change in the code. The rest of this guide is entirely GitHub/AWS console and DNS work.
01

Create the GitHub repository

This becomes the single source of truth for the site — and the trigger for every future deploy.

Create the repo

At github.com/new, create a repository named marketpartner-site (or similar). Leave it empty — don't initialize with a README, since you already have one.

Push the code

If you're comfortable with git, unzip the download and run this from inside the dist folder:

# from inside the unzipped folder
git init
git add .
git commit -m "Initial site"
git branch -M main
git remote add origin https://github.com/<your-username>/marketpartner-site.git
git push -u origin main

No git installed, or would rather skip the command line? GitHub's web uploader works fine for a static site: open the new repo, click Add file → Upload files, and drag in everything from the unzipped folder (including the hidden .github folder — you may need to enable "show hidden files" in your file browser to see it).

Once pushed, refresh the repo page — you should see six HTML files, the README, and a .github/workflows folder.
02

Quick live preview (optional)

Before touching AWS, GitHub Pages gives you a free, real URL in about a minute — a good way to sanity-check the export worked before investing in the AWS setup.

Turn on Pages

In the repo, go to Settings → Pages. Under "Build and deployment", set Source to Deploy from a branch, branch main, folder / (root), then Save.

GitHub will publish the site at https://<your-username>.github.io/marketpartner-site/ within a minute or two. Click through the nav, the mobile menu, and a couple of subpages to confirm everything works outside of claude.ai.

This step is entirely optional and doesn't affect the AWS setup below — treat it as a checkpoint, not a destination. You can leave Pages on as a permanent staging URL, or turn it off later.
03

Create the S3 bucket

S3 will store and serve the actual files. In the AWS Console, go to S3 → Create bucket.

Bucket settings

  • Bucket name: marketpartner.com (matching the domain makes bucket policies and future debugging simpler, though it isn't strictly required once CloudFront is in front of it).
  • Region: whichever is closest to your team — it has no effect on visitors once CloudFront is added.
  • Block Public Access: leave on (all four boxes checked). CloudFront will read from the bucket privately via Origin Access Control, so the bucket itself never needs to be public — the more secure and current approach, replacing the older "public bucket + S3 website endpoint" method.

Upload the files

Open the new bucket, click Upload, and add the six HTML files (skip .github and README.md — those are for the repo, not the live site).

04

CloudFront: HTTPS, speed, and a real domain

CloudFront is AWS's CDN — it puts the site on servers close to every visitor, and it's how S3 content gets HTTPS and a custom domain.

Request the certificate first

In AWS Certificate Manager — importantly, in the us-east-1 (N. Virginia) region regardless of where the bucket lives, since that's the only region CloudFront reads certificates from — request a public certificate for:

marketpartner.com
www.marketpartner.com

Choose DNS validation. ACM will give you a CNAME record to add at your DNS provider; the certificate issues automatically once that record is detected (usually within minutes to a few hours).

Create the distribution

In CloudFront → Create distribution:

  • Origin domain: select your S3 bucket from the dropdown (not the "website endpoint" — the plain bucket option, since Origin Access Control handles the private read).
  • Origin access: Origin Access Control (OAC) — create a new control setting and accept the default. CloudFront will show you a bucket policy to paste into S3's Permissions tab afterward; copy it across.
  • Viewer protocol policy: Redirect HTTP to HTTPS.
  • Alternate domain names (CNAMEs): marketpartner.com and www.marketpartner.com.
  • Custom SSL certificate: select the one requested above.
  • Default root object: index.html — without this, visiting the bare domain shows an error instead of the homepage.
One extra setting worth adding: subpage links in this site are plain filenames (registration-sites.html, not clean URLs), so no rewrite rules are needed for those. If you'd like visitors to reach pages without the .html, that's a CloudFront Function/Lambda@Edge step — worth doing later, not required to launch.
05

Point marketpartner.com at CloudFront

Once the distribution is deployed (status changes from "Deploying" to "Enabled" — typically 5–15 minutes), it has a *.cloudfront.net domain. Point your real domain at it.

If DNS is on Route 53Otherwise (GoDaddy, Namecheap, etc.)
Add an A record (Alias) for both marketpartner.com and www, pointing directly at the CloudFront distribution — Route 53 offers this as a built-in alias target. Add a CNAME for www pointing to the *.cloudfront.net address. For the bare/apex domain, most registrars now support "ALIAS" or "ANAME" records that behave like Route 53's alias — check your provider's docs for the exact name.

DNS changes can take anywhere from a few minutes to 24–48 hours to fully propagate, depending on the previous record's TTL.

06

Wire up auto-deploy

The deploy.yml workflow already in the repo handles this — it just needs credentials.

Create a deploy-only IAM user

In IAM → Users → Create user, create one named e.g. github-deploy, with programmatic access only (no console password). Attach a policy scoped to just this bucket and distribution rather than full admin access:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:PutObject", "s3:DeleteObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::marketpartner.com",
        "arn:aws:s3:::marketpartner.com/*"
      ]
    },
    {
      "Effect": "Allow",
      "Action": "cloudfront:CreateInvalidation",
      "Resource": "*"
    }
  ]
}

Generate an access key for this user (Security credentials tab) and keep the key ID and secret somewhere safe — the secret is only shown once.

Add the secrets to GitHub

In the repo, go to Settings → Secrets and variables → Actions and add:

  • AWS_ACCESS_KEY_ID / AWS_SECRET_ACCESS_KEY — from the IAM user above.
  • AWS_REGION — the region the bucket was created in, e.g. eu-west-2.
  • AWS_S3_BUCKET — marketpartner.com.
  • CLOUDFRONT_DISTRIBUTION_ID — found on the distribution's detail page in CloudFront.

From the next push to main onward, the workflow uploads the changed files and clears the CloudFront cache automatically — edit locally, push, and the live site updates within a minute or two.
